This lesson covers two designs that interviewers often ask back to back, because they are the same idea underneath: typeahead (search suggestions as you type) and nearby search (the places, or drivers, around a point). In both, a request arrives with a partial key. For typeahead it is a string prefix. For nearby search it is a region of the map. The answer has to be the best few matches out of hundreds of millions, in tens of milliseconds, over and over.

The shared lesson is precompute the answer and make the key the index. You cannot scan 150 million phrases on each keystroke, and you cannot compute the distance to 200 million businesses on each map pan. So in both designs you build a structure offline where the partial key points straight to a small, already-ranked answer: a trie node that holds its own top ten, or a geohash cell that holds its own places. What differs is how the data changes. Suggestions are rebuilt every hour from logs. Places change a few times a second. Drivers move 300,000 times a second, and that one difference changes the whole design, which is why the lesson ends with moving objects as a contrast.

Part A is typeahead, Part B is nearby search, and Part C is what changes when the points move.

Part A — Typeahead suggestions

Step 1 — Clarify the requirements

Functional, in scope

  • As the user types into a search box, return the top 10 completions of the current prefix, ranked by popularity.
  • Popularity is recency-weighted: a phrase that trended in the last few hours should beat one that was popular last year.
  • Suggestions are lightly personalised: the user's own recent searches appear first.
  • A denylist can remove a phrase (legal takedown, hate, spam) and the removal must take effect within minutes, not at the next rebuild.
  • Case-insensitive, prefix match on the whole phrase (typing new y suggests new york weather).

Out of scope (say it out loud)

The search results page itself, spelling correction as a full system (we will mention the edit-distance fallback), mid-word or infix matching (york suggesting new york), and ads in the suggestion list. Each is a real feature, and naming them shows you know where this system's edges are.

Non-functional

  • Latency: suggestions must feel instant. For that the server p99 needs to be under 20 ms, which leaves room for the network and still keeps end-to-end p99 under about 100 ms. A suggestion that shows up after the user has typed the next character is useless.
  • Throughput: hundreds of thousands of suggestion requests per second (see the estimate below). This is one of the highest-QPS endpoints a company runs.
  • Freshness: a new trend should appear within an hour, and a breaking one within about 10 minutes through a fast path. Full rebuilds can be daily.
  • Availability over consistency: suggestions that are a few minutes stale, or that differ slightly between two replicas, are fine. Returning nothing is acceptable too. Search still works without suggestions, so this service must never block the search box.

What the numbers decide

  • 650k requests/s at peak is too much for a database lookup per request, but it is easy for an in-memory structure. The trie lives in RAM on the serving boxes, and each box answers from local memory in microseconds.
  • The top-K lists are three times larger than the trie itself. Storing ten completions at every one of 900M nodes is the expensive part. Two fixes follow. First, store pointers to terminal nodes, not copies of the phrase strings. Second, only keep top-K lists for nodes whose subtree has real traffic. Deep nodes like javascript array prototype fla are cheap to compute on demand, because their subtree is tiny.
  • ~150 GB per full copy fits on one large machine, but only just, and it grows. So we partition for memory and replicate for QPS. These are two independent choices, and it helps to keep them apart when you explain the design.
  • 360 GB/day of logs is a batch problem, not a streaming one. Aggregate offline, rebuild, and ship a snapshot.

A common wrong answer is "I will store the phrases in a SQL table and run LIKE 'jav%'". A B-tree can serve a prefix range, but it returns every phrase with that prefix. Ranking them means sorting thousands of rows on each keystroke, and for a one-character prefix it means millions. The whole point of the design is to precompute the ranking.

## Global suggestions (cacheable at the CDN, identical for every user in a locale)

## Personal suggestions (private, never cached at the edge)

  Authorization: Bearer ...
  -> 200 { items: [ { text: "javascript closures", kind: "history",
                      last_used: "2026-09-21T10:02:00Z" } ] }

## Logging (fire-and-forget, batched by the search service, not the browser)

POST /internal/v1/query-log   [{ q, locale, session_hash, ts, clicked_rank? }]
  -> 202

API decisions worth defending

  • GET with cacheable, normalised keys. Lowercase, trim and collapse spaces before building the URL, so Java, java and java all hit one cache entry. Normalising on the server as well is necessary but not enough, because the CDN keys on the raw URL.
  • A v (snapshot version) in the response. When a request fans out to several shards, the aggregator can see that shards disagree during a rollout. It also lets you tie a bad suggestion to the build that produced it.
  • Personalisation is a separate, uncacheable call (or it is merged at the edge). Mixing a user's history into the global response would make every response private and wipe out the CDN hit rate.
  • 204 or an empty list, never an error, when nothing matches. The client should silently show nothing.

Step 4 — Data model

Why store pointers in the top-K lists rather than strings? A popular phrase like javascript tutorial appears in the top-K list of every one of its 19 prefixes. Storing the 19-byte string 19 times per phrase, across 150M phrases, is where the memory goes. An 8-byte pointer to the terminal node, which has a parent pointer to rebuild the text (or an id into a phrase table), cuts that by more than half.

Why a compressed (radix) trie? Most long phrases have a unique tail. After javascript tutorial f there may be only one path, or beginners. A radix trie merges single-child chains into one edge labelled with the whole substring. In a phrase dictionary this often removes most of the nodes, and it shortens the pointer walk.

Step 5 — The core algorithm: a trie with top-K at every node

The naive trie answers suggest("ja") by walking the whole subtree under ja and sorting. That subtree can hold millions of phrases, and a phrase like system design interview questions is 33 levels deep. Instead, each node caches the best K phrases in its subtree. A query then walks only the prefix, which is at most about 20 hops, and reads a list. Here is the whole idea, with offline build, query, the incremental bump used for trending terms, and the disk snapshot:

STORED = 5     # keep a few spares per node so a denylist filter can still fill SERVED
SERVED = 3

class Node:
    __slots__ = ("children", "weight", "top")
    def __init__(self):
        self.children: dict[str, "Node"] = {}
        self.weight = 0                  # score of the phrase that ENDS here (0 = not a phrase)
        self.top: list[tuple[int, str]] = []   # best-first [(score, phrase)], len <= STORED

def rank(cands):
    # Highest score first; ties broken alphabetically so results are deterministic.
    return sorted(cands, key=lambda t: (-t[0], t[1]))[:STORED]

class Trie:
    def __init__(self):
        self.root = Node()

    # ---------- offline build: insert everything, then fill tops bottom-up ----------
    @classmethod
    def build(cls, scored_phrases):
        t = cls()
        for phrase, score in scored_phrases:
            node = t.root
            for ch in phrase:
                node = node.children.setdefault(ch, Node())
            node.weight += score
        t._fill(t.root, "")
        return t

    def _fill(self, node, prefix):
        cands = [(node.weight, prefix)] if node.weight else []
        for ch, child in node.children.items():
            self._fill(child, prefix + ch)
            cands.extend(child.top)          # a child's top-K is all the parent needs
        node.top = rank(cands)

    # ---------- online read: O(len(prefix)), no subtree walk ----------
    def suggest(self, prefix, deny=frozenset()):
        node = self.root
        for ch in prefix.lower():
            node = node.children.get(ch)
            if node is None:
                return []
        return [p for _, p in node.top if p not in deny][:SERVED]

    # ---------- incremental bump (trending fast path) ----------
    def bump(self, phrase, delta):
        path, node = [self.root], self.root
        for ch in phrase:
            node = node.children.setdefault(ch, Node())
            path.append(node)
        node.weight += delta
        new = node.weight
        for n in reversed(path):             # terminal node back up to the root
            others = [t for t in n.top if t[1] != phrase]
            n.top = rank(others + [(new, phrase)])
            if (new, phrase) not in n.top and len(n.top) == STORED:
                break                        # not good enough here -> not good enough above

    # ---------- snapshot to disk: pre-order "char, weight, child count" ----------
    def dump(self):
        out = []
        def walk(n, ch):
            out.append(f"{ch}{n.weight}/{len(n.children)}")
            for c in sorted(n.children):
                walk(n.children[c], c)
        walk(self.root, "^")
        return "|".join(out)      # "|" because phrases contain spaces

    @classmethod
    def load(cls, blob):
        tokens = iter(blob.split("|"))
        def read():
            tok = next(tokens)
            ch, rest = tok[0], tok[1:]
            weight, kids = map(int, rest.split("/"))
            n = Node(); n.weight = weight
            for _ in range(kids):
                c, child = read()
                n.children[c] = child
            return ch, n
        t = cls(); _, t.root = read()
        t._fill(t.root, "")                   # tops are NOT stored; recompute on load
        return t


logs = [("java", 900), ("javascript", 1400), ("java tutorial", 300),
        ("jaguar", 250), ("japan", 700), ("jam recipe", 120),
        ("jazz", 410), ("jav", 5)]
t = Trie.build(logs)
print("ja   ->", t.suggest("ja"))
print("jav  ->", t.suggest("jav"))
print("jaz  ->", t.suggest("jaz"))
print("xyz  ->", t.suggest("xyz"))
print("ja (deny japan) ->", t.suggest("ja", deny={"japan"}))

t.bump("jaguar", 1500)                        # a new car launch goes viral
print("after bump, ja ->", t.suggest("ja"))

blob = t.dump()
print("snapshot nodes:", blob.count("|") + 1, "  head:", blob[:30])
t2 = Trie.load(blob)
print("reloaded ja ->", t2.suggest("ja"))

What the code is teaching

  • Bottom-up build is linear. A parent's top-K is the merge of its children's top-K lists plus its own weight. You never look deeper than one level, so the build costs O(nodes × K), not O(nodes × subtree size).
  • The query does no ranking. suggest costs O(len(prefix)) pointer hops plus a list read. That is how you get microseconds.
  • Store a few spares. We keep 5 and serve 3 (in production, keep about 15 and serve 10). When the denylist removes japan, jazz moves up without a rebuild. If you store exactly K, every filtered item leaves a hole.
  • Increments are cheap, decrements are not. bump walks from the terminal node back to the root. It stops as soon as the phrase fails to make a node's list, because if it is not in the top five for jag, it cannot be in the top five for ja. A decrease is different. If a phrase falls out of a list, the replacement could be anywhere in the subtree, and only children's lists can tell you which. This is the real reason trie updates are done as an offline rebuild, and it is worth saying explicitly.
  • The snapshot does not store the top-K lists. A pre-order walk writes each node as its character, weight and child count. That is enough to rebuild the shape, and _fill recomputes every list on load. The file is small, and a server that restarts can load and fill it in minutes.

Reads never touch the offline side. Trie servers only answer queries. They load a finished snapshot and swap it in, and a small streaming path pushes breaking trends between builds.

What each component owns

  • Client: debounces keystrokes, cancels stale requests, caches recent responses, and prefetches. It removes most requests before they are ever sent (see Step 9).
  • CDN edge: caches responses for short prefixes (one to three characters) for 60 to 300 seconds. There are only about 30,000 three-character prefixes, and they get the most traffic.
  • Aggregator: normalises the prefix, looks up the partition map, fans out to one or more trie shards, merges their top-K lists, applies the denylist, and merges in personal history. It is stateless.
  • Trie servers: hold one partition of the trie in RAM and answer top(prefix). They are read-only between snapshot swaps.
  • Prefix cache (Redis): stores the merged, post-denylist responses for hot prefixes that need a fan-out, so the aggregator does not merge the same shards thousands of times per second.
  • Batch aggregation plus EMA table: turns raw logs into one score per phrase (Step 8).
  • Trie builder: builds and fills each partition, validates it (size, spot checks against the old version), and publishes a versioned snapshot.
  • Trending detector: a streaming job that sees a phrase jump, for example 50x its baseline in 5 minutes, and calls the bump fast path on live servers.

Step 7 — Walk one keystroke end to end

sequenceDiagram participant U as User participant C as Client participant E as CDN edge participant A as Aggregator participant R as Prefix cache participant T as Trie shards participant H as Personal history U->>C: types jav, then keeps typing C->>C: debounce 100 ms, check local cache for jav C->>C: abort in-flight request for ja C->>E: GET /suggest?q=jav&n=10&locale=en-IN E-->>C: HIT (short prefix, max-age 120) — done Note over C,E: Longer prefix javasc misses the edge C->>E: GET /suggest?q=javasc E->>A: forward (miss) A->>A: normalise, look up partition map: shard G-M only A->>R: GET sugg:v812:en:javasc R-->>A: miss A->>T: top(javasc, 15) on one replica (hedged after 8 ms) T-->>A: 15 (score, phrase) pairs A->>A: drop denylisted, keep 10 A->>R: SETEX sugg:v812:en:javasc 300 A-->>E: 200 {v: 812, items: [...]} Cache-Control max-age=60 E-->>C: 200 C->>H: GET /suggest/personal?q=javasc (parallel, private) H-->>C: [javascript closures] C->>U: personal first, then global, dedupe

Most keystrokes never reach the origin. They are removed by debounce or the local cache, or answered at the edge. The ones that do reach the origin touch one shard, one cache key and no disk.

The order of operations, and why

  1. Debounce, then abort. The client waits until the user pauses before it sends a request, and it cancels the previous in-flight request so a slow ja response cannot overwrite a fast jav response. Without this, suggestions visibly flicker backwards.
  2. Local cache before network. Backspacing from javas to java should cost nothing, because the client already has that response.
  3. Edge cache for short prefixes. A handful of keys covers a large share of traffic, and they are identical for every user in a locale.
  4. The partition map decides the fan-out. javasc lives on exactly one shard. A single-character prefix like j may span two shards and needs a merge, which is exactly why short prefixes are the ones we cache hardest.
  5. Ask for 15 and serve 10. The spares absorb denylist removals.
  6. Hedge the shard call. If the first replica has not answered in 8 ms, which is about its p95, send the same request to a second replica and use whichever answers first. The request is idempotent and cheap, so hedging cuts the p99 at the cost of about 5% extra load.
  7. Personal history is fetched in parallel and merged on the client. The global response stays cacheable, and the private part never touches a shared cache.

Step 8 — Building and updating the trie offline

Updating the live trie on every search would mean 35,000 writes per second, each one walking up to the root and taking locks that the 650,000 reads per second then wait on. Reads matter more than freshness here, so updates are batched offline.

The pipeline

  1. Log. The search service writes every submitted query to Kafka, including the query text, locale, a hashed session id, the timestamp and whether a result was clicked. Log submitted searches, not keystrokes. Otherwise the suggestions learn to suggest themselves.
  2. Aggregate hourly. A batch job (Spark, or MapReduce in older stacks) groups by (locale, normalised phrase) and counts. It drops phrases below a threshold, such as fewer than 50 distinct sessions per day. That removes typos, private information such as names and phone numbers, and the long tail that would never make a top-10 list anyway.
  3. Score with decay. Rather than re-summing a sliding 30-day window, keep one exponentially weighted moving average per phrase and update it with the latest hour's count.
  4. Build. Build each partition from the score table, fill the top-K lists bottom-up, validate, and write a versioned snapshot to object storage.
  5. Swap. Each trie server loads the new snapshot next to the old one, warms it, and switches a single pointer. If a replica does not have room for two copies, drain it from the load balancer, load the new snapshot, and put it back, one replica at a time. This is the same as a primary/standby flip: the standby loads while the primary serves.
import math, random

HALF_LIFE_H = 24.0                      # a search's weight halves every day
ALPHA = 1 - 0.5 ** (1 / HALF_LIFE_H)    # per-hour smoothing factor for the EMA

def ema_update(old_score, this_hour_count):
    """One hourly job step. No need to keep the whole history: the old score
    already summarises it, so the job reads old score + one hour of counts."""
    return old_score * (1 - ALPHA) + this_hour_count * ALPHA

# 7 days of hourly counts for two phrases
evergreen = [400] * 168                              # steady every hour
launch    = [0] * 160 + [3000] * 8          # a launch trending for the last 8 hours

The phrases it gets wrong are the rare ones, and those are below the index cut-off anyway. You can only sample if you do not need the long tail, so say that condition out loud.

Removing a phrase

A legal takedown cannot wait for tonight's build. Two layers handle it. A denylist filter on every aggregator and trie server applies to results as they are served (this is why we store spares). The denylist is small, is pushed as a config update within a minute, and matches normalised phrases and, optionally, patterns. The next build then drops the phrase from the input, so it is removed from the structure too. The filter stays in place as defence in depth.

Ranking beyond counts

The score that goes into the trie can be any offline-computed number. In practice it blends decayed frequency, click-through rate on the suggestion (a suggestion people ignore should sink), freshness, locale and region (football means different sports in London and Dallas), and a quality penalty for adult or low-value content. Build a separate trie, or a separate score column, per locale. Anything that depends on the individual user is applied at serving time, not baked into the trie.

Step 9 — The client: the cheapest request is the one you never send

The client removes more load than any server-side optimisation. A simulation of one person typing javascript tutorial, with realistic gaps between keystrokes:

# Keystroke timestamps (ms) for someone typing "javascript tutorial":
# quick bursts, one pause after "javascript", a longer think before "tutorial".

    """A request fires when the user has been idle for debounce_ms.

    sent = []

        if nxt - ts >= debounce_ms and i + 1 >= min_chars:

    return sent

The other client techniques:

  • Minimum length. Do not call the server for the first character. Ship the top suggestions for all 26 (or all locale-specific) one-character prefixes as a small static file on page load.
  • Cancel in-flight requests with AbortController when a newer keystroke arrives, and discard any response whose prefix no longer matches the input box.
  • Local response cache, keyed by prefix, for the session. This makes backspace free.
  • Prefetch. When the response for jav arrives, the client can speculatively request java, the most likely next prefix. Or the server can return a slightly deeper result set for short prefixes, so the client can filter locally for the next character or two.
  • Warm the connection early. Open the TLS connection, and keep an HTTP/2 connection alive, as soon as the search box gets focus. A cold TLS handshake on the first keystroke costs more than the whole server-side lookup.
  • Local history. Recent searches stored on the device are the most reused suggestions of all, and they need no network call.

Step 10 — Partitioning, replication and caching

The trie needs to be split across machines once one copy no longer fits in memory, or once rebuilding it on one machine takes too long. There are three ways to split it, and interviewers expect you to compare all three.

import bisect, zlib

Pick capacity-based ranges. Handle traffic skew with replication, giving the ca… shard six replicas instead of three, and handle short-prefix fan-out with caching. Hash partitioning looks elegant, but it throws away the property that makes a trie useful, which is that one prefix lives in one place.

Replication and load balancing

Every shard has at least three replicas across availability zones. The aggregator holds the partition map, a small versioned table from range to replica set, and does client-side load balancing, picking the least-loaded replica rather than round-robin. Because trie servers are read-only, replicas never need to coordinate. Each one loads the same snapshot file, so they are identical by construction.

Caching

A few prefixes carry a large share of the traffic, so a cache in front of the tries earns its keep at three levels: the client's local cache, the CDN for short prefixes, and Redis for merged multi-shard responses. Put the snapshot version in every cache key (sugg:v812:…). A new build then creates new keys that start cold, and nothing ever has to be invalidated. The same versioned-key trick appears in the caching lesson and the food-delivery capstone. For a one-hour build cycle, the cold start is visible as a brief rise in shard traffic. Pre-warm the top 100k prefixes from the new snapshot before the flip.

Fault tolerance

  • A replica dies: the aggregator's health checks remove it within seconds, and the other replicas absorb its share. Nothing is lost, because the server has no unique state.
  • A replica restarts: it pulls the latest snapshot from object storage, runs load and _fill, and rejoins. Budget minutes, not hours, and keep the snapshot on local SSD so a restart does not depend on object storage.
  • A bad build ships (for example, empty results for a whole locale): the builder's validation step should catch it, by comparing the top 1,000 prefixes against the previous version and refusing to publish if they differ by more than 30%. If it gets through anyway, rollback is simply pointing servers at the previous snapshot version.
  • The whole suggest service is down: the client times out after about 150 ms and shows nothing. Search still works. This is why it must be a separate service with its own failure domain.

Step 11 — Personalisation

Keep a small per-user list, the last 50 or so searches with timestamps, in a key-value store keyed by user id, with a copy cached on the device. At serving time, filter that list by the prefix, rank by recency, and place up to three matches ahead of the global results, removing duplicates. Personal results come first because a user's own history has by far the highest click-through rate. Do this merge at the edge or on the client so the global response stays cacheable. Heavier personalisation, such as re-ranking the global list by a user's interests, belongs in a small re-ranking model that runs on the 15 candidates after retrieval. The trie is for retrieval. It is not where per-user logic belongs.

Step 14 — Why the obvious SQL query fails

Most candidates start with WHERE lat BETWEEN ? AND ? AND lng BETWEEN ? AND ? and an index on each column. It is correct, and it is slow. A B-tree on lat returns a band of latitude that wraps the whole planet. A B-tree on lng returns a band of longitude that runs pole to pole. The database either scans one band and filters, or intersects two large id lists. A composite index on (lat, lng) does not help either, because a B-tree can only range-scan its first column. Here is a simulation:

Step 15 — Fixed grids, and why they need to adapt

Divide the map into equal squares and store a grid_id on each place, with an index on it. If the cell size is at least the search radius, any circle is covered by the user's cell and its 8 neighbours, so a query becomes nine equality lookups instead of a planet-wide band scan. In memory, this is a hash map from cell id to a list of place ids. With 6M land cells and 200M places, it is about 3 GB.

The flaw is density. The estimate above gives an average of 34 places per 5 km cell. A downtown cell holds tens of thousands, and an ocean cell holds none. Queries in a dense area filter a huge list, and the empty cells waste memory. Using one cell size everywhere guarantees that some areas will be wrong. Adapt the cell size to density: subdivide where it is crowded. Geohash lets you choose the resolution per query. A quadtree chooses it per region, automatically.

Step 16 — Geohash: a grid you can range-scan

A geohash repeatedly halves the world, alternating longitude and latitude, and writes down one bit per halving. The bits are interleaved and grouped in fives as base-32 characters. Each extra character makes the cell 32 times smaller, and a shared prefix means a shared cell. So "places in this cell" becomes WHERE geohash LIKE 'tdr1v%', a single B-tree range scan, in any ordinary database, Redis sorted set or search engine. Here is an encoder, the neighbour computation, and a working radius query over a sorted index:

import math
from collections import defaultdict

BASE32 = "0123456789bcdefghjkmnpqrstuvwxyz"   # no a, i, l, o

def encode(lat, lng, precision=6):
    """Interleave bits: even bits halve longitude, odd bits halve latitude.
    Every 5 bits become one base-32 character."""
    lat_lo, lat_hi, lng_lo, lng_hi = -90.0, 90.0, -180.0, 180.0
    out, bits, ch, even = [], 0, 0, True
    while len(out) < precision:
        if even:
            mid = (lng_lo + lng_hi) / 2
            if lng >= mid: ch, lng_lo = (ch << 1) | 1, mid
            else:          ch, lng_hi = ch << 1, mid
        else:
            mid = (lat_lo + lat_hi) / 2
            if lat >= mid: ch, lat_lo = (ch << 1) | 1, mid
            else:          ch, lat_hi = ch << 1, mid
        even, bits = not even, bits + 1
        if bits == 5:
            out.append(BASE32[ch]); bits, ch = 0, 0
    return "".join(out)

def bbox(gh):
    lat_lo, lat_hi, lng_lo, lng_hi = -90.0, 90.0, -180.0, 180.0
    even = True
    for c in gh:
        v = BASE32.index(c)
        for shift in range(4, -1, -1):
            bit = (v >> shift) & 1
            if even:
                mid = (lng_lo + lng_hi) / 2
                lng_lo, lng_hi = (mid, lng_hi) if bit else (lng_lo, mid)
            else:
                mid = (lat_lo + lat_hi) / 2
                lat_lo, lat_hi = (mid, lat_hi) if bit else (lat_lo, mid)
            even = not even
    return lat_lo, lat_hi, lng_lo, lng_hi

def neighbours(gh):
    """The 8 surrounding cells: step one cell-width from the centre and re-encode."""
    lat_lo, lat_hi, lng_lo, lng_hi = bbox(gh)
    dlat, dlng = lat_hi - lat_lo, lng_hi - lng_lo
    clat, clng = (lat_lo + lat_hi) / 2, (lng_lo + lng_hi) / 2
    out = []
    for dy in (1, 0, -1):
        for dx in (-1, 0, 1):
            if dx == dy == 0: continue
            lat = max(min(clat + dy * dlat, 89.999999), -89.999999)
            lng = (clng + dx * dlng + 180) % 360 - 180          # wrap the antimeridian
            out.append(encode(lat, lng, len(gh)))
    return out

def haversine_m(a, b):
    (la1, lo1), (la2, lo2) = map(lambda p: (math.radians(p[0]), math.radians(p[1])), (a, b))
    h = math.sin((la2 - la1) / 2) ** 2 + math.cos(la1) * math.cos(la2) * math.sin((lo2 - lo1) / 2) ** 2
    return 2 * 6_371_000 * math.asin(math.sqrt(h))

import bisect

    "Filter Coffee Co": (12.97160, 77.59430), "Dosa Corner":   (12.97160, 77.59670),
    "Brew Lab":         (12.97480, 77.59990), "Idli Express":  (12.96650, 77.58710),
    "Far Away Diner":   (13.03500, 77.59700), "Chai Point MG": (12.97550, 77.60640),
}
index = sorted((encode(lat, lng, STORE_PRECISION), name, lat, lng)
               for name, (lat, lng) in places.items())
keys = [row[0] for row in index]

def precision_for(radius_m):
    """Longest prefix whose cell is still at least `radius` tall and wide, so the
    centre cell plus its 8 neighbours is guaranteed to cover the whole circle."""
    for p in range(STORE_PRECISION, 0, -1):
        la0, la1, lo0, lo1 = bbox(encode(12.97, 77.59, p))
        if min(haversine_m((la0, lo0), (la1, lo0)), haversine_m((la0, lo0), (la0, lo1))) >= radius_m:
            return p
    return 1

def nearby(lat, lng, radius_m, k=10, with_neighbours=True):
    p = precision_for(radius_m)
    centre = encode(lat, lng, p)
    cells = [centre] + (neighbours(centre) if with_neighbours else [])
    cands = []
    for c in cells:                                      # one range scan per cell
        lo, hi = bisect.bisect_left(keys, c), bisect.bisect_left(keys, c + "~")
        cands.extend(index[lo:hi])
    hits = [(haversine_m((lat, lng), (r[2], r[3])), r[1]) for r in cands]
    return p, len(cells), len(cands), sorted(h for h in hits if h[0] <= radius_m)[:k]

What to point out

  • The boundary trap. Cafe A and cafe B are 54 m apart but in different cells, so a lookup of the centre cell alone finds only one place. You must search the centre cell plus its 8 neighbours. Candidates who say "just prefix-match the user's geohash" have missed this. The trap is worse at big boundaries. Two points either side of the equator or the prime meridian can share no prefix at all.
  • Choose precision from the radius. Pick the longest prefix whose cell is at least as tall and wide as the radius. Then nine cells are guaranteed to cover the circle. Store the fine hash once, at 9 characters, and query at whichever coarser length the radius needs. One index serves every zoom level.
  • Cells are not square, and they shrink toward the poles. Odd precisions are roughly square. Even ones are twice as wide as they are tall. Longitude degrees also get shorter away from the equator. This is why the helper measures the real cell with haversine instead of using a lookup table.
  • Always finish with an exact distance filter. Nine cells cover more area than the circle, so the index returns candidates and haversine decides the answer.
  • This is what Redis GEO does. GEOADD stores a 52-bit interleaved geohash as a sorted-set score, and GEOSEARCH … BYRADIUS performs this nine-cell range scan and filter. The same idea sits behind Elasticsearch geo_point and PostGIS's geohash functions. PostGIS's main index is an R-tree, covered below.

Step 17 — QuadTree: a grid that adapts itself

A quadtree starts with one cell for the whole region. When a cell holds more than a fixed number of places (say 400), it splits into four equal quadrants and pushes its places down. Dense areas become deep and fine-grained. Empty areas stay as one big leaf. Only leaves hold places, and a query descends only into cells that intersect the search circle.

import math, random

class QuadTree:
    """A region quadtree over a square. A leaf holds up to `cap` points; the insert
    that would overflow it splits the leaf into 4 equal quadrants and pushes its
    points down. Dense areas get deep, small cells; empty areas stay one big leaf."""
    def __init__(self, x, y, size, cap=4, depth=0):
        self.x, self.y, self.size, self.cap, self.depth = x, y, size, cap, depth
        self.points = []            # only leaves hold points
        self.kids = None            # [SW, SE, NW, NE] once split

    def _child_for(self, px, py):
        half = self.size / 2
        i = (1 if px >= self.x + half else 0) + (2 if py >= self.y + half else 0)
        return self.kids[i]

    def insert(self, px, py, pid):
        if self.kids is not None:
            return self._child_for(px, py).insert(px, py, pid)
        self.points.append((px, py, pid))
        if len(self.points) > self.cap and self.depth < 12:     # depth cap: duplicates
            half = self.size / 2
            self.kids = [QuadTree(self.x + dx * half, self.y + dy * half, half,
                                  self.cap, self.depth + 1)
                         for dy in (0, 1) for dx in (0, 1)]
            pts, self.points = self.points, []
            for p in pts:
                self._child_for(p[0], p[1]).insert(*p)

    def query(self, cx, cy, r, stats):
        # Prune any cell whose square cannot intersect the circle.
        nx = min(max(cx, self.x), self.x + self.size)
        ny = min(max(cy, self.y), self.y + self.size)
        if math.hypot(nx - cx, ny - cy) > r:
            return []
        stats["nodes"] += 1
        if self.kids is None:
            stats["leaves"] += 1
            return [p for p in self.points if math.hypot(p[0] - cx, p[1] - cy) <= r]
        return [p for k in self.kids for p in k.query(cx, cy, r, stats)]

    def leaves(self):
        if self.kids is None:
            yield self
        else:
            for k in self.kids:
                yield from k.leaves()

Reading the result

  • 90% of the places sit in 402 small leaves downtown, some only 125 m across, while the suburbs are covered by a few large leaves up to 16 km. Every leaf holds at most 50 places, so no query ever filters a huge list. A fixed grid cannot do this.
  • The same 500 m query visits 110 nodes downtown and 4 in the suburbs. Work is proportional to how many places are near you, not to how many places exist in total.
  • Memory is tiny. With 200M places and 400 per leaf, you get 500k leaves and about 167k internal nodes. The internal nodes' child pointers total a few megabytes. Almost all of the memory is the place entries themselves, about 3 GB, so the whole tree fits comfortably on one server and is replicated.
  • Finding neighbours. To expand a search when the user's leaf has too few results, walk up through parent pointers and back down into siblings, or link the leaves in a doubly-linked list in space-filling-curve order. Both let you grow the search ring until you have K results or reach the maximum radius.
  • Insertions are a descent plus an occasional split, which is fine at 5 edits per second. It is not fine at 300,000 per second (Part C).

The geo index answers only one question: which place ids are near here, with their scores. Details come from a cache by id. Writes flow through CDC into the index asynchronously, so a new place appears within seconds to minutes.

Two phases: the geo index finds and ranks candidate ids in memory, and then a batch read by id fills in the display fields. Neither phase scans anything proportional to the size of the dataset.

The order of operations, and why

  1. Compute the cells before routing. The radius decides the precision, and the precision decides the nine cells. Only then do you know which shards to ask, often just one.
  2. Filter by category inside the index. Store a category bitmask next to each entry, so "cafes near me" does not return 50 candidates that are mostly dentists.
  3. Each shard returns its own top N with a score. The aggregator merges them. This is the same top-K merge as the typeahead fan-out, and the same one used for ranking popular places across partitions.
  4. Exact distance and final ranking happen after the merge, on a few hundred candidates, so the scoring formula can be as elaborate as you like.
  5. Batch-fetch details by id with one MGET. Places are read far more often than they are edited, so an LRU cache of place cards has a very high hit rate. The database only sees misses.
  6. Too few results? Widen the search, either to the next ring of cells or one precision coarser, and repeat, up to a maximum radius. Do not return an empty map because the user is in a rural area.

Step 19 — Partitioning, replication, caching and ranking

Partitioning: by region or by place id?

Shard by region (city, geohash prefix)Shard by place_id hash

BalanceSkewed. Manhattan's shard is much bigger and busier than rural Montana's.Even, by construction

RebalancingSplit a region, which needs a routing-table changeConsistent hashing moves about 1/N of the data
Tree shape per shardOne contiguous treeEvery shard has its own sparse tree over the whole map

Many textbook answers choose place-id hashing for its balance. That is defensible, but name the cost: every query becomes an N-way scatter-gather, and tail latency grows with N. The stronger answer is region sharding with adaptive boundaries. Use geohash-prefix or S2-cell ranges sized by load rather than by area, the same capacity-based cutting as the trie, and a routing table the aggregator caches. A dense city gets several shards and a rural country gets one. Hot spots are handled by adding replicas to the busy shard, not by spreading every query across the whole fleet. When the index fits on one machine, which at 3 to 12 GB it does, the simplest answer is no partitioning, just replicas. Say so, and give the growth number that would change your mind.

Replication and rebuilding a dead index server

Each shard has a primary that applies index updates and replicas that serve reads. A replica may be a few seconds behind, which is fine for "a new cafe appears". If every replica of a shard dies, a new server must rebuild the index. Scanning 200M database rows to find the ones that hash to this shard is slow. Keep an index-server map, a small service mapping shard to the set of (place_id, lat, lng) it owns, and a fresh server bulk-loads from it in minutes. The map is itself replicated, and it can always be rebuilt from the database as a last resort. Better still, have index servers write periodic snapshots to object storage, just like trie servers.

Caching

Cache place cards by id with LRU. A small fraction of places (famous restaurants, landmarks) takes most of the detail views. Cache whole search responses for popular (cell, category) pairs, such as "coffee near Times Square", with a short TTL. Snap the user's location to the cell so everyone standing in the same 150 m cell shares one key. Never cache by raw lat/lng, because no two phones report the same coordinates.

Ranking

Distance alone gives poor results. The closest place is often the worst one. Score is a blend: w1 · proximity + w2 · rating (with a Bayesian prior, so a single 5-star review does not win) + w3 · popularity + w4 · text relevance + w5 · open now. Ratings and popularity change slowly and are expensive to rewrite in a live index, so a batch job recomputes them once or twice a day in a quiet period and publishes them to the index shards. "Top 100 popular places within 5 km" is each shard returning its local top 100 and the aggregator merging them.

At 65,000 times more writes than the directory, the quadtree's weakness shows. Each position update is a move: find the old leaf, remove the driver, find the new leaf, insert, and perhaps split or merge. Doing that 300,000 times per second on a shared tree means lock contention on the read path. The design changes in four ways:

  • Split "latest position" from "spatial index". Each ping overwrites one entry in a hash map keyed by driver id, a 37 MB table sharded by driver id. The spatial index is refreshed from that table every 10 to 15 seconds, and only for the roughly 6% of pings that actually crossed a cell boundary. A driver shown on the map 10 seconds late is acceptable. A lock-contended index is not.
  • Prefer fixed cells to an adaptive tree. For moving objects, a flat map from geohash or H3 cell to driver set per city, or Redis GEO keyed per city, beats a quadtree. A cell move is two set operations, and nothing ever rebalances. If you do keep a quadtree, add hysteresis: let a leaf grow 10 to 20% beyond its limit before splitting, and merge only well below it, so a busy intersection does not split and merge every few seconds.
  • Push or pull to the viewer. Pushing each nearby driver's movement to 2M open maps is about 160 MB/s of fan-out, plus the complexity of subscribing viewers to drivers as cars enter and leave the viewport. Having the client poll nearby every 5 seconds is 400k simple, cacheable queries per second, and they can share a cell-keyed cache. Most systems poll for the "cars on the map" view and push only for the one driver on your active trip, where accuracy matters. That push goes over the same WebSocket tier as chat.
  • Matching is a write, not a read. Choosing a driver needs an atomic claim so that two riders cannot get the same car. That is a compare-and-set on driver state, walked through in the food-delivery capstone. The nearby query only produces candidates.

"Nearby friends" is the same problem at lower write rates (phones report every 30 to 60 s) and with a privacy twist. You only index users who have opted in, you compute friend-distance only among friend pairs, and you round locations before showing them.

Step 21 — Observability

  • Typeahead: suggestion click-through rate (the business signal), keystrokes saved per search, p99 by prefix length, CDN and Redis hit rate, snapshot age per shard, and the share of responses that had to be filled from spares after the denylist.
  • Nearby: zero-result rate by region (this catches index holes), candidates scanned per query (this catches hot cells), p99 by shard, CDC lag, and place-card cache hit rate.
  • Moving objects: location age at match time (how stale the chosen driver's position was), pings per second per shard, and cell-move rate.

The trade-off summary — how to close

  • Precomputed top-K in the trie, not ranking at query time. We pay about 3x memory to make the read path a pointer walk, the only way to serve 650k QPS in single-digit milliseconds.
  • Offline rebuild plus a trending fast path, not live updates. Increments are cheap and decrements are not, so correctness comes from the rebuild and freshness from bump.
  • Capacity-based range partitions, not hash. One prefix lives in one place. Skew is solved with replicas and short-prefix fan-out with caches.
  • The client is part of the design. Debounce, abort, local cache and prefetch remove most requests before they exist.
  • Geohash or S2 cells in an existing store for places, not a lat/lng B-tree. "Near in space" has to mean "near in the key". Always query nine cells, then filter exactly.
  • Quadtree for adaptive density where you own the service. Flat cells and a latest-position hash for moving objects. The write rate decides the structure.
  • Index returns ids, cache returns details. Both designs keep the hot structure tiny by storing pointers, not payloads.

The sentence that wins both interviews

"The query is a partial key, so I will make the partial key the index and precompute the answer at each key: top-K at each trie node, and places per geohash cell. Reads become a short walk plus a small list. The hard part is keeping that precomputation fresh, so I will pick the update strategy from the write rate: hourly rebuilds for suggestions, CDC for places, and a separate latest-position table for anything that moves."
