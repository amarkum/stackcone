A rate limiter caps how often a client may call an API. Interviewers ask it on its own and as a piece of every public API. Goals: stop abuse, protect downstreams, keep fair usage, return HTTP 429 with a Retry-After header.

1. Requirements

  • Limit by API key, IP, or user id; different rules per endpoint (POST /login stricter than GET /public).
  • Low latency on the allow path (in-memory or Redis, not a disk DB).
  • Accurate enough across many app servers. Slight softness is OK; double-charging is not the failure mode here.
  • Optional: burst vs sustained rate, distributed, admin-configurable rules.

2. Algorithms

  • Token bucket (default answer): tokens refill at rate r, bucket holds at most c. Allows bursts up to c, then steady r.
  • Leaky bucket: queue requests and drain at a fixed rate. Smooths bursts; can add latency.
  • Fixed window: count hits in the current minute. Cheap, but a burst at the window edge can be 2× the limit.
  • Sliding window log: store timestamps, drop those older than the window. Accurate, more memory.
  • Sliding window counter: weight the previous window by overlap. Good Redis compromise.
import time

class TokenBucket:
    def __init__(self, rate, capacity):
        self.rate, self.capacity = rate, capacity
        self.tokens, self.last = capacity, time.monotonic()

    def allow(self):
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

bucket = TokenBucket(rate=5, capacity=10)
print(sum(bucket.allow() for _ in range(12)))   # 10 tokens, then deny

The gateway is the usual place: one policy, before you spend app CPU. Redis holds shared counters so all boxes agree.

3. Distributed implementation

Local memory on each app server is wrong: 10 boxes × 100 req/s = 1000 req/s to the backend. Use Redis: INCR + EXPIRE for a fixed window, or a Lua script for a token bucket so refill and consume are atomic. Shard Redis by client key (consistent hash). For huge fan-out, an in-process cache of the decision for a few milliseconds reduces Redis QPS.

# Sliding window counter (previous + current minute)
def allow(redis, key, limit, now_s):
    window = now_s // 60
    prev, cur = f"{key}:{window-1}", f"{key}:{window}"
    # counts would come from Redis MGET + INCR
    counts = {prev: 40, cur: 30}
    frac = (now_s % 60) / 60
    approx = counts[cur] + counts[prev] * (1 - frac)
    return approx < limit

print(allow(None, "user:42", 100, 60 + 15))

4. Rules and response

  • Return 429, X-RateLimit-Limit, X-RateLimit-Remaining, Retry-After.
  • Hard block scrapers; softer limits for paying customers (token bucket with larger capacity).
  • Login and password-reset endpoints need tighter limits plus captcha, separate from the global API quota.

Soft vs hard

At the edge, slightly exceeding the limit under Redis lag is acceptable. For billing or SMS send, use a stronger atomic check.
