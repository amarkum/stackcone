Design a URL shortener like TinyURL or bit.ly: users submit a long URL and get a short one; visiting the short link redirects. It is the first full product interview most people meet, and it uses IDs, caching, hashing and analytics.

1. Requirements

  • Functional: create a short URL, redirect, optional custom alias and expiry, click counts, optional user accounts.
  • Out of scope for v1 unless asked: QR codes, A/B links, full BI dashboards.
  • Non-functional: redirect p99 under 50–100 ms, very high availability, read-heavy (often 100:1), codes not sequentially guessable, 301/302 choice explicit.

2. Estimates

new_urls_per_day = 100_000_000 / 30          # 100M new URLs per month
writes_per_sec = new_urls_per_day / 86_400     # ~40/s
read_write_ratio = 100
reads_per_sec = writes_per_sec * read_write_ratio   # ~4,000/s

records_5_years = 100_000_000 * 12 * 5          # 6 billion
bytes_per_record = 500
storage_tb = records_5_years * bytes_per_record / 1e12
print(round(writes_per_sec), round(reads_per_sec), round(storage_tb, 1))
Output
39 3858 3.0

Forty writes/s and 4k reads/s is modest; 3 TB in five years fits one database. Caching is the main lever, not sharding on day one.

3. API and data model

POST /api/v1/urls       { long_url, custom_alias?, expires_at? } -> { short_url }
GET  /{code}             -> 301 or 302 Location: long_url
GET  /api/v1/urls/{code} -> metadata and click summary

table urls (
  code        VARCHAR(10) PRIMARY KEY,
  long_url    TEXT NOT NULL,
  created_at  TIMESTAMP,
  expires_at  TIMESTAMP NULL,
  user_id     BIGINT NULL
)
-- clicks go to a queue, not this table on the redirect path

4. Generating the short code

Seven base62 characters give 62^7 ≈ 3.5 trillion codes, far more than 6 billion rows.

  • Hash the URL (SHA-256, take 7 chars). Collisions need a retry with a salt.
  • Counter + base62: encode a Snowflake or ticket id. No collisions; sequential codes are guessable unless you permute bits.
  • Random 7 chars plus a unique index, retry on conflict. Simple and unguessable.
ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"

def base62(n: int) -> str:
    if n == 0:
        return ALPHABET[0]
    out = []
    while n:
        n, r = divmod(n, 62)
        out.append(ALPHABET[r])
    return "".join(reversed(out))

print(base62(125), base62(3_500_000_000), len(ALPHABET) ** 7)

flowchart LR U[Browser] --> LB[Load balancer] LB --> APP[App] APP --> Redis[(Redis)] Redis -->|miss| DB[(Postgres / KV)] APP -->|click event| Q[(Queue)] Q --> Agg[Analytics workers]

Redirects hit Redis first. The database is the source of truth. Clicks are fire-and-forget onto a queue.

5. High-level design

  • Stateless app servers behind a load balancer.
  • Redirect: cache-aside Redis keyed by code, long TTL, LRU. Hottest links never touch the DB.
  • Write: validate URL, allocate code, insert. Custom aliases check uniqueness and reserved words (api, admin).
  • Store: PostgreSQL + replicas, or DynamoDB (always get-by-key). Shard by hash(code) only when the cluster is full.
  • Analytics: publish {code, ts, country, referrer} to Kafka/SQS; aggregate in ClickHouse or daily rollup tables.

6. Trade-offs

  • 301 vs 302: 301 lets browsers cache the hop (cheaper, hides later clicks). 302 keeps every click visible. Most shorteners use 302.
  • Abuse: rate-limit creates, malware URL scans, captcha for anonymous users.
  • Expiry: check expires_at on read; a sweeper deletes old rows.
  • Multi-region: replicate the KV globally; DNS failover. Accept brief replication lag on brand-new links.

How to present it

Talk through the six steps, state assumptions aloud, sketch as you go. Clear structure beats a perfect encoding scheme.

Try it yourself

Extend the design with per-link click analytics (clicks per day, top countries) without slowing down redirects. Which components do you add, and where does each piece of data live?
