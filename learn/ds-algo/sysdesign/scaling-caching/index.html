When one server is no longer enough you have two options: make it bigger (vertical scaling) or add more of them (horizontal scaling). Vertical is simple but has a ceiling and a single point of failure. Horizontal scales further and survives machine loss, but the app must share no local state.

flowchart LR U[Users] --> DNS DNS --> LB[Load balancer] LB --> A1[App 1] LB --> A2[App 2] LB --> A3[App N] A1 --> C[(Redis cache)] A2 --> C A3 --> C A1 --> DB[(Primary DB)] A2 --> R[(Read replica)] A3 --> R

Any app box can serve any request. Session and files live in Redis or object storage, not on the box.

Stateless services and load balancers

Application servers should be stateless: no user data only in a server's RAM. A load balancer sits in front and spreads traffic.

  • Algorithms: round robin, least connections, consistent hash by client or cookie.
  • Health checks pull dead servers out of rotation.
  • Layer 4 balances TCP; layer 7 (HTTP) can route by path (/video vs /api).
  • Run two balancers or a managed one so the balancer is not a new single point of failure.

Caching

A cache stores expensive results close to the caller. Memory is roughly a thousand times faster than a typical database round trip. Layers:

  • Browser and CDN: static files, images, even cacheable API JSON.
  • Application cache (Redis, Memcached): sessions, hot rows, rendered feeds.
  • Database buffer: pages and query plans.

Cache-aside pattern

The app checks the cache, falls back to the database on a miss, then fills the cache.

import json, redis
r = redis.Redis()

def get_user(user_id):
    key = f"user:{user_id}"
    cached = r.get(key)
    if cached:                              # hit
        return json.loads(cached)
    user = db.query_user(user_id)           # miss
    r.setex(key, 300, json.dumps(user))     # 5-minute TTL
    return user

def update_user(user_id, data):
    db.update_user(user_id, data)
    r.delete(f"user:{user_id}")             # invalidate

Write strategies, TTL and stampede

  • Write-through: write cache and DB together. Fresh reads; slower writes.
  • Write-back: write cache, flush DB later. Fast, risk of loss.
  • TTL plus explicit delete on writes. LRU eviction when memory is full.
  • Stampede: a hot key expires and thousands of requests hit the DB. Mitigate with a lock, jittered TTLs, or refresh-ahead.

Consistent hashing

When you add or remove a cache node, hash(key) % N moves almost every key. Consistent hashing places nodes on a ring; a key maps to the next node clockwise. Adding a node only remaps its slice. Virtual nodes spread load so one physical box is not a hotspot.

CDN

For global users put static assets and cacheable pages on a CDN. It cuts latency and origin load because bytes are served from a nearby edge PoP.
