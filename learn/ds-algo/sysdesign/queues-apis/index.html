Not everything should happen while the user waits. Email, video transcode and search indexing can run later. Message queues decouple the requester from the worker so spikes, failures and scale are isolated.

flowchart LR API[API] -->|publish| Q[(Queue / log)] Q --> W1[Worker] Q --> W2[Worker] W1 --> DB[(DB / S3)] W2 --> DB Q -.->|poison messages| DLQ[(Dead-letter queue)]

The HTTP request returns after enqueue. Workers scale independently. Failed messages land in a DLQ after N retries.

Queues and logs

A producer puts a message on a queue; consumers process it. RabbitMQ and SQS are queues; Kafka is a durable log that many consumer groups can replay.

  • Smooths spikes — 10,000 signups become a steady drain on workers.
  • Isolates failure — email down means messages wait, not 500s for users.
  • Pub/sub — one event, many subscribers (billing, shipping, analytics).
# producer (in the web request)
queue.publish("send_welcome_email", {"user_id": 42})
print({"status": "created"})          # respond immediately

# consumer (background worker)
def handle(message):
    user = {"id": message["user_id"], "email": "ada@example.com"}
    print("email", user["email"], "Welcome!")

handle({"user_id": 42})

Delivery and idempotency

Most queues are at-least-once: a crash before ack can redeliver. Consumers must be idempotent. Same idea on APIs: an Idempotency-Key header so a retried payment is not charged twice.

def charge(message, processed=None):
    processed = processed or set()
    key = message["idempotency_key"]
    if key in processed:
        return "skip"
    processed.add(key)
    return "charged"

print(charge({"idempotency_key": "pay-1"}))
print(charge({"idempotency_key": "pay-1"}))
Output
charged
skip

Retries, timeouts, circuit breakers

  • Retry with exponential backoff plus jitter.
  • After N failures, send the message to a dead-letter queue.
  • Every outbound call needs a timeout.
  • A circuit breaker stops calling a sick dependency so failures do not cascade.

Realtime: polling, SSE, WebSockets

  • Short polling is simple and wasteful.
  • Long polling / SSE — server holds the request until an event (notifications, one-way).
  • WebSockets — bidirectional; chat, presence, collaborative editors. Sticky sessions or a pub/sub bus so any socket server can wake the right connection.

API design

  • Version (/v1/). Cursor pagination, not giant offsets.
  • Correct status codes; structured errors.
  • Rate limits belong at the edge (full design in lesson 7). A token bucket is the usual first sketch.

Design for failure

Assume every network call can be slow, fail or duplicate. Reliable systems are built from components that expect that.
