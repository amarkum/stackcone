Design a video platform in the mould of YouTube or Netflix: creators upload files, the platform turns each one into something every device on every network can play, and hundreds of millions of viewers press play and expect the first frame in under two seconds, with no spinner for the rest of the video. Around that core sit search, view counts, comments, recommendations and content protection.

The single most useful framing for this interview is that you are designing two systems that barely touch, plus a small database between them:

  • An ingest and processing pipeline — resumable uploads, deduplication, transcoding into a bitrate ladder, packaging, thumbnails, captions. Low request rate (tens of uploads per second), enormous compute, latency measured in minutes, and correctness means "never lose a creator's upload".
  • A delivery system — manifests, segments, a multi-tier CDN, adaptive bitrate in the player. Millions of requests per second and tens of terabits per second of egress, latency measured in milliseconds, and correctness means "the spinner never appears".
  • A metadata and engagement layer in between — video rows, view counts, likes, comments, watch history, search and recommendations. Ordinary web-scale problems, except for the hot-key problem when one video goes viral.

Candidates who draw one box labelled "video service" that both accepts uploads and streams bytes have already lost the thread. The API servers in this design never touch a video byte in either direction.

Step 1 — Clarify the requirements

Functional, in scope

  • Upload: a creator uploads a file of up to 12 hours or 256 GB, from a phone on a flaky network or a studio on fibre. The upload survives disconnects and resumes where it stopped.
  • Process: the platform transcodes the file into several resolutions and codecs, generates thumbnails and auto-captions, and tells the creator when it is watchable.
  • Watch: viewers play any public video on web, mobile and TV, seek anywhere, and quality adapts to their connection. Playback resumes where they left off on another device.
  • Discover: search by title, description and tags; a home feed and "up next" recommendations (sketch only).
  • Engage: view counts, likes and dislikes, comments.
  • Protect: private and unlisted videos, and DRM for premium (Netflix-style) content.

Explicitly out of scope

Live streaming (a different latency model — mention it as a follow-up), ads insertion, creator monetisation and payouts, the copyright-claims workflow, channels and subscriptions beyond what the feed needs, the ML models themselves, and moderation tooling. Name each one so the interviewer knows you know it exists.

Non-functional, with numbers

  • Scale: 500M daily active viewers, 6 plays each per day; 5M uploads per day averaging 7 minutes.
  • Playback latency: time to first frame p50 under 1 s and p95 under 2 s; rebuffering under 0.5% of watch time. These are the metrics that correlate with people leaving.
  • Processing latency: a short video is watchable at low resolution within a minute or two of upload completing; full quality within tens of minutes even for long 4K files.
  • Durability: an accepted upload is never lost — eleven nines on the source file. This is stronger than for any rendition, because renditions can always be regenerated from the source.
  • Availability: playback 99.99%. Uploads and processing can tolerate a delayed queue; playback cannot tolerate an outage.
  • Consistency: eventual almost everywhere. A new video appearing in search a minute late is fine; view counts lagging by seconds is fine. The exceptions are privacy (a video set to private must stop playing quickly) and the creator seeing their own upload status accurately.

Step 2 — Back-of-the-envelope estimation

What the numbers actually decide

  • 31–62 Tbps of egress is the entire problem. No data centre serves that from one place, and no transit contract makes it affordable. This number alone forces a multi-tier CDN with caches embedded inside ISP networks, and makes egress price per GB the biggest line in the budget.
  • 3.1M segment requests per second are all static-file GETs. They must be served by caches that never call an application server — which is why the player fetches plain files named in a manifest, rather than calling a streamVideo(offset) API that returns bytes.
  • 35k–104k play starts per second is the only per-play load on the application tier: fetch metadata, authorise, return a manifest URL. That is a normal, cacheable web workload.
  • 58 uploads per second is small, but each one is gigabytes. The upload API handles metadata only; bytes go straight from the client to object storage using pre-signed URLs.
  • 4.6 PB of new storage per day and 1.7 EB per year means storage tiering is mandatory. Most of the catalogue is almost never watched, and should not sit on the same storage class as this week's hits.
  • ~100k cores of transcoding is a batch compute fleet that runs on cheap, pre-emptible capacity, which means every transcode task must be small, idempotent and restartable.
  • Read:write is 600:1 for plays, and far higher for segment reads. Every read path gets a cache; the write paths get queues.

Step 3 — API design

Three families of endpoint: the upload control plane, the playback control plane, and engagement. None of them carry video bytes.

API decisions worth defending

  • The server never proxies bytes. A pre-signed URL is a time-limited, single-object permission signed with the storage service's key. The client talks to object storage directly, which scales without us and keeps gigabytes out of API server memory and sockets.
  • Upload is a session, not a request. A session id, numbered parts and a "what have you got" endpoint make resume trivial. A single POST with a 6 GB body fails at 97% on a train and starts again from zero.
  • complete returns 202, not 201. The video exists but is not watchable; the state field and a push notification tell the creator when it is.
  • There is no streamVideo(offset, codec, resolution) call. Older designs sketch an API that returns a byte stream from an offset. In practice the client declares its capabilities once, receives a manifest, and then fetches static segments from the CDN, choosing codec and resolution itself; seeking to an offset is just requesting a different segment number. The server-side part of "resume from offset" is the progress endpoint.
  • Playback authorisation happens once, at /play, and is carried to the CDN as a signed token. The edge validates a signature locally in microseconds; it never calls back to an auth service per segment.
  • View and QoE events are batched and fire-and-forget. The player must never block playback on analytics.

Step 4 — Data model

Five kinds of data, five storage choices. The video metadata is the smallest and the one people spend the most time on; the bytes are the biggest and the simplest.

Modelling decisions to explain

  • Metadata and bytes are separate systems. A row in videos is about 1 KB; a video is gigabytes. The database stores keys, never blobs. Putting video files in a database (or in a distributed filesystem that the metadata service manages directly) couples two very different scaling curves.
  • The source file is kept forever, the renditions are disposable. Every rendition can be regenerated from src/ when a better codec appears, which is exactly what happens every few years. That is why the source gets the strongest durability and the renditions can live on cheaper tiers or be deleted for cold videos.
  • manifest_version is in the object path. When AV1 renditions are added to an old video, a new version directory is written and the pointer bumped; CDN caches of the old manifest simply age out instead of needing a global purge.
  • Thumbnails are a separate, small-object problem. A page shows 20–40 thumbnails and one video, so thumbnail reads outnumber video plays by an order of magnitude. Billions of 10–50 KB files are inefficient as individual objects on disk (a seek each); store them packed (a Bigtable-like store or a haystack-style packed file with an in-memory offset index) and serve them from the CDN like everything else.
  • Counters are a separate table from videos. The video row is read-mostly and cached; the counter row is write-heavy. Mixing them means every view invalidates the cached video row.
  • Comments are keyed by video, with a bucket. A viral video gets millions of comments; bucketing by time (video_id#2026-09) keeps any one partition bounded.

Step 5 — Sharding the metadata

At billions of video rows and 100k+ reads per second, the metadata has to be partitioned. There are two obvious keys, and the interviewer wants to hear the trade-off.

  • Shard by creator (user_id / channel_id). "All videos by this channel" is a single-shard query, which is nice. But creators are wildly uneven — one channel has 40,000 uploads and a billion views, most have three — so both storage and traffic pile onto whichever shards hold the big channels, and rebalancing means moving an entire channel at once. Anything that is not per-creator (search, "get video by id" when you do not know the owner) scatters to every shard.
  • Shard by video_id. Rows spread evenly because ids are effectively random. "Get video by id" — the call made on every play — hits exactly one shard. The per-channel listing now needs a secondary index, which you maintain as its own table sharded by channel_id. The remaining problem is a viral video: one row, one shard, a million reads a second. That is not a sharding problem; it is a caching problem.
import random, hashlib
from collections import Counter

rng = random.Random(7)
SHARDS, N_VIDEOS, N_CREATORS = 16, 200_000, 20_000

def shard(key: str) -> int:
    return int(hashlib.md5(key.encode()).hexdigest(), 16) % SHARDS

# Creators are skewed (a few upload thousands); so are views (a few videos go viral).
creator_w = [1 / (i + 1) ** 1.1 for i in range(N_CREATORS)]
owners = rng.choices(range(N_CREATORS), weights=creator_w, k=N_VIDEOS)
view_w = [1 / (i + 1) ** 1.1 for i in range(N_VIDEOS)]
rng.shuffle(view_w)                       # popularity is unrelated to video id

def skew(counter: Counter) -> float:      # hottest shard vs a perfectly even split
    return max(counter.values()) / (sum(counter.values()) / SHARDS)

for name, key in (("user_id ", lambda v: f"u{owners[v]}"), ("video_id", lambda v: f"v{v}")):
    rows, reads = Counter(), Counter()
    for v in range(N_VIDEOS):
        s = shard(key(v))
        rows[s] += 1
        reads[s] += view_w[v]
    print(f"shard by {name}: rows skew {skew(rows):.2f}x   read skew {skew(reads):.2f}x")
Output
shard by user_id : rows skew 3.07x   read skew 3.97x
shard by video_id: rows skew 1.02x   read skew 2.73x

The simulation shows the point precisely: sharding by video id fixes storage skew completely (1.02x), but a handful of viral videos still make one shard nearly three times hotter than average. No choice of shard key fixes a single hot row. The answer is a cache in front of the database — the hot video's metadata served from memory in every app server and replicated across cache nodes — so the database only sees the cold tail.

  • Routing: use consistent hashing (or a directory of key ranges, as Vitess and Spanner do) so adding a shard moves only a fraction of the keys, and a dead node's ranges can be taken over by replicas.
  • Replication: each shard is a primary with two or more replicas across zones. Replica lag means a creator who just edited a title might read the old one; route that creator's own reads to the primary for a few seconds after a write (read-your-writes), and let everyone else read replicas.
  • Search does not scatter to shards at all. It goes to a separate search index fed by change-data-capture, so the "query all shards and merge" problem that appears in naive designs never arises.

The left half is a batch pipeline driven by events; the right half is a read path that ends in caches. They share only the object store and the metadata database, and the API tier never touches video bytes.

What each component owns

  • Upload service — creates upload sessions, signs part URLs, checks quotas, verifies the multipart completion, runs exact-hash dedupe, and emits upload.completed. Stateless apart from the metadata row.
  • Transcode orchestrator — turns one upload into a DAG of tasks, tracks their state durably in transcode_tasks, retries failures, and publishes video.ready (and later rendition.added) events. It schedules work; it never encodes.
  • Encode workers — pull one task at a time (split, encode one chunk at one rung, stitch, package, thumbnail), read inputs from and write outputs to object storage. Dumb, horizontally scalable, pre-emptible.
  • Playback service — the only per-play application call. Reads cached metadata, enforces visibility, region and entitlement rules, filters the manifest to what the device can decode, and returns a signed manifest URL plus a DRM license URL.
  • CDN tiers — serve manifests and segments. Edge caches validate the URL token locally and never call the application.
  • Event ingest and view counter — absorb player heartbeats, dedupe, aggregate and flush counts in batches.
  • Search indexer and recommendations — consumers of the event log. If they are down, uploads and playback are unaffected.

Step 7 — The upload path

Resumable, chunked, direct to storage

The upload is split into numbered parts, each sent as its own HTTP request to a pre-signed URL. Object stores support this natively — S3 multipart upload, GCS resumable uploads, Azure block blobs — and the open tus protocol standardises the same idea over plain HTTP for when you run your own upload servers. The two differ in who tracks progress:

S3-style multipart with pre-signed URLstus (resumable upload protocol)
Bytes go toThe object store directlyYour tus servers, which then write to storage
Progress tracked byPart numbers and ETags; the client or your service lists partsA single byte offset (HEAD returns Upload-Offset)
ParallelismParts upload in parallel, in any orderSequential by default; parallel via the concatenation extension
ConstraintsParts at least 5 MiB (except the last), at most 10,000 partsAny chunk size

Part size is a real decision. Too small and a 400 GB studio master exceeds the part limit; too large and every dropped connection throws away a large part. The planner below starts at 16 MiB and grows only when the file needs it.

import math

MiB, GiB = 1024 ** 2, 1024 ** 3
MIN_PART, MAX_PARTS = 5 * MiB, 10_000       # S3 multipart limits (last part may be smaller)

def plan_parts(size_bytes: int, target_part=16 * MiB) -> tuple[int, int]:
    """Pick a part size: at least 5 MiB, and big enough that we stay under 10,000 parts."""
    part = max(MIN_PART, target_part, math.ceil(size_bytes / MAX_PARTS))
    part = math.ceil(part / MiB) * MiB        # round up to a whole MiB
    return part, math.ceil(size_bytes / part)

for label, size in (("phone clip", 180 * MiB), ("1h 1080p", 6 * GiB),
                    ("2h 4K ProRes", 400 * GiB)):
    part, n = plan_parts(size)
    print(f"{label:>13}: {n:>6,} parts of {part // MiB} MiB")

# ---- Resume after a dropped connection: ask the server what it has ----
class UploadSession:
    def __init__(self, size, part):
        self.size, self.part = size, part
        self.n = math.ceil(size / part)
        self.etags: dict[int, str] = {}      # part_number -> ETag (server's record)

    def missing(self) -> list[int]:
        return [p for p in range(1, self.n + 1) if p not in self.etags]

    def put_part(self, number: int):         # the client PUTs to a pre-signed URL
        self.etags[number] = f"etag-{number}"

s = UploadSession(6 * GiB, 16 * MiB)

The creator's device only ever talks to the upload service for small JSON calls. The object store holds the bytes from the first part onwards, and the pipeline starts from a durable event rather than a synchronous call.

The order of operations, and why

  1. Create the metadata row before any bytes move. The video id exists from the start, so every part, log line and retry is attributable. A row stuck in UPLOADING for days is swept.
  2. Dedupe on the declared hash before accepting bytes. If the client sends a SHA-256 up front and it matches an existing source, the upload can be skipped entirely — seconds instead of an hour of upload and 4 core-minutes per minute of transcoding.
  3. Verify on complete. The completion call lists every part's ETag; the store assembles them atomically. Missing parts return 400 PART_MISSING and the client resumes.
  4. Publish upload.completed through an outbox. The state change and the event commit together, so a crash cannot leave a video in PROCESSING that no worker ever hears about.
  5. Mark READY as soon as the first rendition is packaged, not when the whole ladder is done. Higher rungs are added to the manifest as they finish.

Deduplication, at three levels

A large share of uploads are re-uploads: the same file, the same clip re-encoded, a clip with a watermark or borders, a short excerpt of a longer film. Duplicates waste storage, transcode compute, CDN cache space and network, and they pollute search results. Detect them in layers, cheapest first:

  • Exact bytes — SHA-256 of the file, checked before upload. Catches the identical re-upload. Free, but trivially defeated by a single changed byte.
  • Perceptual fingerprint — decode keyframes, downscale to a tiny greyscale grid, and hash the pattern of brightness differences; plus an audio fingerprint of spectral peaks. Re-encoding, resizing, borders and small overlays leave these fingerprints almost unchanged, so near-duplicates match within a small Hamming distance. Run it on the first minute as soon as those parts land, so a duplicate can be flagged while the upload is still in progress.
  • Segment matching — index fingerprints per few seconds of content, so an excerpt matches the middle of a longer original. This is the basis of copyright-match systems and is expensive, so it runs asynchronously after the video is live.

What to do on a match is a product decision, not a storage one. A creator's own identical re-upload can reuse the existing renditions (store a pointer, not a copy). A higher-quality version of an existing video can replace the old source. Someone else's copyrighted film gets routed to the claims workflow. Silently discarding an upload because it looks like another one is never the answer.

Step 8 — The transcoding pipeline

A phone uploads 8 Mbps H.264 at 1080p; a studio uploads 400 GB of ProRes. Neither can be sent to a viewer on a 2 Mbps phone connection. Transcoding produces a bitrate ladder: the same content at several resolutions and bitrates, in several codecs, cut into short segments so the player can switch between them.

Two refinements matter at scale. Per-title encoding picks the ladder per video: a static lecture looks perfect at 1080p and 1.5 Mbps, while a football match needs 6 Mbps, so a fixed ladder either wastes bytes on the lecture or starves the match. Analysing complexity first and choosing bitrates per title saves 20–40% of egress on typical catalogues. Audio is separate: two or three audio rungs (64, 128, 256 kbps) per language, packaged independently so that one set of video segments serves every audio track.

Codecs: the compute-versus-bandwidth trade

  • H.264/AVC — decodes in hardware on essentially every device ever made. Cheap to encode. The mandatory baseline.
  • VP9 — roughly 30–40% smaller than H.264 at equal quality, royalty-free, broadly supported in browsers and Android. Several times more expensive to encode.
  • HEVC/H.265 — similar efficiency to VP9, strong on Apple devices and TVs, with patent-licensing complexity.
  • AV1 — roughly another 30% smaller than VP9, royalty-free, hardware decode on recent phones and TVs. Encoding costs an order of magnitude more than H.264.

The design consequence: encode H.264 for everything, and spend AV1 or VP9 compute only on videos with enough views to pay it back in egress savings (Step 15 does the arithmetic). The playback service filters the manifest by the codecs the device declares, so old devices never see an AV1 rendition they cannot decode.

Split, encode in parallel, stitch

Encoding a 2-hour 4K film on one machine takes days. The trick is that video is already divided into independently decodable units: a GOP (group of pictures) starts with a keyframe that carries a full image, followed by frames that only store differences. Cut the source at keyframe boundaries into 5–10 second chunks and each chunk can be encoded on a different machine; the outputs join seamlessly because each still starts on a keyframe. Force keyframes at fixed intervals (for example every 2 seconds) in every rung, so that segment boundaries line up across the whole ladder — that alignment is what lets a player switch rungs between any two segments.

Each box is a task in the DAG, and each encode box is really N parallel chunk tasks. The orchestrator releases a task when its inputs exist; the 360p branch runs at the highest priority so the video becomes watchable first.

The simulation schedules the chunk tasks of a 2-hour 4K upload across a worker pool, lowest rung first, and reports when each rung is complete and packaged.

import heapq

# Encoding cost in worker-seconds per second of video, per rung (illustrative, H.264).
RUNGS = [("360p", 0.5), ("240p", 0.3), ("480p", 0.9), ("720p", 1.8),
         ("1080p", 4.0), ("2160p", 16.0)]          # listed in PRIORITY order
PRIORITY = {name: i for i, (name, _) in enumerate(RUNGS)}

def build_dag(duration_s: int, chunk_s: int):
    """split -> encode(chunk, rung) x N -> per-rung package. Returns encode tasks."""
    chunks = range(0, duration_s, chunk_s)          # GOP-aligned cut points
    tasks = []
    for name, cost in RUNGS:
        for start in chunks:
            length = min(chunk_s, duration_s - start)
            tasks.append((PRIORITY[name], start, name, cost * length))
    return sorted(tasks)                            # low-res first, in timeline order

def schedule(tasks, workers: int, split_s=30, package_s=20):
    free = [split_s] * workers                      # every worker waits for the split step
    heapq.heapify(free)
    rung_done: dict[str, float] = {}
    for _, _, rung, cost in tasks:
        t = heapq.heappop(free) + cost
        heapq.heappush(free, t)
        rung_done[rung] = max(rung_done.get(rung, 0), t)
    return {r: t + package_s for r, t in rung_done.items()}   # + write playlist

duration = 2 * 3600                                  # a 2-hour 4K upload
serial = sum(cost for *_, cost in build_dag(duration, 10))
print(f"one machine, serial: {serial / 3600:,.1f} hours")
for workers in (50, 400):
    done = schedule(build_dag(duration, chunk_s=10), workers)
    line = "  ".join(f"{r} {done[r] / 60:5.1f}m" for r, _ in RUNGS)
    print(f"{workers:>3} workers -> {line}")

Making the pipeline reliable

  • Every task is idempotent and addressed by its output. The task id encode:h264:720p:chunk-0042 determines the output key. Running it twice overwrites the same object with the same bytes, so retries are always safe.
  • Leases, not locks. A worker claims a task with a lease (say 5 minutes) and heartbeats while it works. A pre-empted spot instance simply stops heartbeating, the lease expires, and another worker picks the task up. Losing a worker costs one chunk, never the whole video.
  • Poison inputs are quarantined. A corrupt file that crashes the encoder three times goes to a dead-letter queue and the video is marked FAILED with a reason the creator can see, instead of looping forever.
  • Priority lanes. Short videos and the first rung of every video go in a fast lane; 4K and AV1 go in a bulk lane that soaks up spare capacity overnight. A 12-hour livestream archive must not delay a thousand 30-second clips.
  • Thumbnails and captions are part of the DAG, not an afterthought: candidate thumbnails from frames with high sharpness and faces, a sprite sheet of tiny frames every few seconds for the seek bar preview, and speech-to-text captions exported as WebVTT per language.

Step 9 — Packaging: HLS and DASH manifests

The player does not download "a video". It downloads a manifest — a small text file listing the available renditions — then a per-rendition media playlist listing segments, then the segments themselves, one at a time.

  • HLS (HTTP Live Streaming, from Apple) uses .m3u8 text playlists. Required for Safari and iOS.
  • DASH (MPEG-DASH) uses an XML manifest, the .mpd. Common on Android, smart TVs and in browsers via Media Source Extensions.
  • CMAF — a common fragmented-MP4 segment format both can reference. Encode and store segments once, and write two small manifests pointing at the same files. Before CMAF, platforms stored every video twice, once per protocol.

Why segments, and why 2–6 seconds

  • Segments are plain static files, so any HTTP cache on earth can serve them. That property is the whole reason HTTP streaming replaced stateful streaming servers.
  • Short segments let the player switch quality quickly and start faster (it needs one segment before first frame). Long segments compress slightly better and mean fewer requests. 4 seconds for VOD and 1–2 seconds (or partial segments) for low-latency live are typical.
  • Seeking is arithmetic. Seek to 11:23 is segment 683 / 4 = 170; the player fetches that segment directly. No server-side offset handling needed.

Step 10 — Playback and adaptive bitrate

From tap to first frame, the budget is about a second: /play call (≈100 ms, cached metadata) → master manifest from the edge (≈30 ms) → media playlist (≈30 ms) → init segment and first media segment (a few hundred ms at the lowest sensible rung). Players cut this further by prefetching the manifest for the thumbnail you are hovering over, starting at a conservative rung, and embedding the first playlist inside the /play response.

After that, the player runs a loop: before each segment, pick a rung. That choice — adaptive bitrate (ABR) — is the entire viewer experience. Pick too high and the buffer drains and the spinner appears; pick too low and a 4K TV shows mush; switch too often and quality visibly pumps. There are two classic families:

  • Throughput-based: measure how fast recent segments downloaded, pick the highest rung under a safety fraction of that estimate. Intuitive, but throughput estimates are noisy on mobile, and the estimate is always about the past.
  • Buffer-based (BBA, and BOLA in dash.js): ignore throughput and pick the rung from how many seconds of video are buffered. A low buffer means play it safe; a full buffer means you can afford a big segment. It uses the buffer as a shock absorber and naturally reaches high quality, but it starts slowly (the buffer is empty at startup) and can be caught by a sudden cliff.

The simulation runs all three strategies — the two classic ones and a hybrid — over the same five-minute commute with a noisy connection and a near-dead tunnel. The digits show the rung chosen for each 4-second segment (0 = 240p, 4 = 1080p).

import random

LADDER = [0.4, 0.8, 1.4, 2.8, 5.0]          # Mbps: 240p, 360p, 480p, 720p, 1080p
SEG_S, MAX_BUF, N_SEGS, DT = 4.0, 30.0, 75, 0.05   # 4 s segments, 5 min of video

# A commute: Wi-Fi, a weak-signal stretch, 4G, a near-dead tunnel, home Wi-Fi.
# Every second is also multiplied by random jitter, as real cellular links are.
PLAN = ((40, 6.0), (70, 1.2), (130, 4.0), (160, 0.5), (1e9, 7.0))
rng = random.Random(2)
JITTER = [rng.uniform(0.3, 1.7) for _ in range(2000)]

def bandwidth(t: float) -> float:
    for until, mbps in PLAN:
        if t < until:
            return mbps * JITTER[int(t)]

def estimate(history):                       # harmonic mean resists one lucky burst
    recent = history[-3:]
    return len(recent) / sum(1 / x for x in recent)

def throughput_rule(buffer_s, history):
    """Classic rate-based: highest rung under 80% of the estimated throughput."""
    if not history:
        return 0
    est = 0.8 * estimate(history)
    return max([i for i, b in enumerate(LADDER) if b <= est], default=0)

def buffer_rule(buffer_s, history, reservoir=6.0, cushion=20.0):
    """BBA-style: the buffer level alone picks the rung. Below the reservoir take
    the lowest rung, above reservoir + cushion the highest, linear in between."""
    if buffer_s <= reservoir:
        return 0
    if buffer_s >= reservoir + cushion:
        return len(LADDER) - 1
    return int((buffer_s - reservoir) / cushion * (len(LADDER) - 1))

def hybrid_rule(buffer_s, history):
    """What real players do: rate-based while the buffer is thin (startup, after a
    seek), buffer-based once it is healthy, and never pick a segment that the
    current throughput could not finish before the buffer hits the reservoir."""
    if buffer_s < 10.0:
        return throughput_rule(buffer_s, history)
    rung, est = buffer_rule(buffer_s, history), estimate(history)
    while rung > 0 and LADDER[rung] * SEG_S / est > buffer_s - 6.0:
        rung -= 1
    return rung

def simulate(rule):
    t = buffer = rebuffer = 0.0
    history, chosen, playing = [], [], False
    for _ in range(N_SEGS):
        rung = rule(buffer, history)
        bits, got, start = LADDER[rung] * SEG_S, 0.0, t
        while got < bits:                        # download in 50 ms steps
            got += bandwidth(t) * DT
            t += DT
            if playing:                          # playback drains the buffer meanwhile
                if buffer > DT:
                    buffer -= DT
                else:
                    rebuffer += DT - buffer      # spinner on screen
                    buffer = 0.0
        history.append(bits / (t - start))       # measured Mbps for this segment
        chosen.append(rung)
        buffer += SEG_S
        playing = True
        if buffer > MAX_BUF:                     # buffer full: pause fetching
            t += buffer - MAX_BUF
            buffer = MAX_BUF
    switches = sum(1 for a, b in zip(chosen, chosen[1:]) if a != b)
    avg = sum(LADDER[r] for r in chosen) / len(chosen)
    return avg, rebuffer, switches, "".join(map(str, chosen))

    print(f"  {trace}")

Reading the result

  • Throughput-based never stalled but left quality on the table (3.17 Mbps average) and switched 26 times, because every noisy measurement moved the choice.
  • Buffer-based reached the best quality but spent 4.65 seconds on a spinner: it had a full buffer, chose a 1080p segment just as the tunnel started, and that single segment took longer to download than the buffer could cover. Real players add more: abandoning a segment mid-download when it is clearly too slow and refetching a lower rung, capping resolution at the screen size (a phone never needs 4K), and much longer buffers on TVs (minutes, not 30 seconds), which makes the buffer-based approach far safer.

Each tier absorbs most of the requests that reach it. The origin sees only the long tail, and the fill job pre-positions tomorrow's popular titles during off-peak hours.

  • Edge — servers placed inside ISP networks (Netflix Open Connect and Google Global Cache work this way) or at internet exchange points. Bytes from an ISP-embedded box never cross a transit link, which is why ISPs host them for free: it saves them money too.
  • Regional — larger caches per country or metro that serve edge misses and small ISPs without their own appliances.
  • Origin shield — one designated cache layer in front of the object store. Without it, a cold video that becomes popular causes every regional cache to miss at once and hit origin simultaneously. The shield collapses those into one origin fetch per segment (request coalescing: the first miss fetches, concurrent misses for the same key wait for it).
  • Origin — object storage holding everything, on tiers from hot to archive.

How much each tier absorbs

Video popularity roughly follows a power law: rank k gets views proportional to 1/ks. The exponent s matters enormously, so the simulation computes hit ratios for two plausible values.

def zipf_mass(k: int, s: float, exact_upto: int = 100_000) -> float:
    """Sum of i^-s for i = 1..k: exact for the head, an integral for the long tail."""
    m = min(k, exact_upto)
    head = sum(i ** -s for i in range(1, m + 1))
    if k <= m:
        return head
    a, b = m + 0.5, k + 0.5
    return head + (b ** (1 - s) - a ** (1 - s)) / (1 - s)

Popularity-based placement

  • Pull-through for the unpredictable: caches fill on demand with LRU or, better, a frequency-aware policy (LFU with ageing, or admission filters that ignore one-hit wonders so a crawler scanning old videos does not flush the hot set).
  • Push for the predictable: a nightly job forecasts what each region will watch tomorrow — a new season of a series, a creator with 50M subscribers who just uploaded — and pre-positions it in off-peak hours when links are idle. This is the heart of Netflix-style delivery, where the catalogue is small and predictable.
  • Rendition-aware placement: cache the rungs people actually watch in that region. An edge serving mostly phones on 4G does not need to hold 4K.
  • Hot-object replication: within one PoP, requests are spread across servers by consistent hashing on the segment URL, so each server holds a distinct slice (no duplicate caching). A viral video would overload its one server, so objects above a request-rate threshold are replicated to several servers in the PoP and requests are spread among them.

Load balancing and steering

The player is steered to an edge by DNS (geo and latency-aware resolution) or anycast, or explicitly: the /play response can name the edge hostname, chosen by a steering service that knows each PoP's load and health. Overloaded servers can redirect a client to a sibling with HTTP 302, but each redirect adds a round trip before the first frame, and redirects across tiers can send a viewer to a distant cache, so steering at the start of the session is preferred to redirecting mid-stream. The player also keeps a list of fallback hosts and fails over itself when a segment request times out.

Step 12 — View counting at scale

A view count looks like UPDATE videos SET views = views + 1. At 35k plays per second, with one launch video drawing a large share of them, that single row becomes the hottest lock in the company. It is also wrong on product grounds: a view should mean someone actually watched (not that a bot requested the manifest), and refreshing the page should not count twice.

import random
from collections import Counter

rng = random.Random(42)
HOT, FLUSH_EVERY_S, MIN_WATCH_S, DEDUPE_WINDOW_S = "v_launch", 10, 30, 3600

def heartbeats(second):
    """5,000 player heartbeats per second: a launch going viral plus 2,000 others."""
    for _ in range(5_000):
        vid = HOT if rng.random() < 0.7 else f"v{rng.randrange(2_000)}"
        viewer = f"u{rng.randrange(200_000)}"               # some viewers repeat
        watched = rng.choice((5, 12, 31, 45, 90, 240))      # seconds watched so far
        yield second, vid, viewer, watched

class ViewAggregator:
    """One instance per stream partition (partitioned by video_id, so no locks)."""
    def __init__(self):
        self.first_seen: dict[tuple, int] = {}   # (video, viewer) -> t; Redis + TTL in prod
        self.pending = Counter()                  # views since the last flush
        self.db = Counter()                       # stands in for the counter store
        self.events = self.db_writes = self.short = self.dups = 0

    def on_event(self, t, vid, viewer, watched):
        self.events += 1
        if watched < MIN_WATCH_S:
            self.short += 1; return               # not a "view" yet
        first = self.first_seen.get((vid, viewer))
        if first is not None and t - first < DEDUPE_WINDOW_S:
            self.dups += 1; return                # refresh spam, replays
        self.first_seen[(vid, viewer)] = t
        self.pending[vid] += 1

    def flush(self):                              # one write per video per window
        for vid, n in self.pending.items():
            self.db[vid] += n                     # UPDATE ... SET views = views + n
            self.db_writes += 1
        self.pending.clear()

agg = ViewAggregator()
for second in range(60):
    for event in heartbeats(second):
        agg.on_event(*event)
    if (second + 1) % FLUSH_EVERY_S == 0:
        agg.flush()

print(f"heartbeats: {agg.events:,}  (naive design = {agg.events:,} row updates)")
print(f"not views: {agg.short:,} under {MIN_WATCH_S}s, {agg.dups:,} already counted")
print(f"views counted for {HOT}: {agg.db[HOT]:,}")
print(f"counter-store writes: {agg.db_writes:,} total, {60 // FLUSH_EVERY_S} on the hot row")
Output
heartbeats: 300,000  (naive design = 300,000 row updates)
not views: 100,263 under 30s, 39,209 already counted
views counted for v_launch: 100,777
counter-store writes: 11,905 total, 6 on the hot row

The design, as the code does it:

  • The player sends heartbeats, not "a view happened". The server decides what counts: a minimum watch time, one view per viewer per video per window, and later, fraud filtering on patterns such as one IP generating thousands of views.
  • Partition the stream by video_id. All events for one video land on one consumer, so dedupe and aggregation need no distributed locks. A single hot video may need its key split across several partitions (video_id#0..7) with a final sum.
  • Aggregate in memory and flush every few seconds, one write per video per window. 300k heartbeats became 11,905 writes, and the viral video's row was touched 6 times instead of 100,777.
  • Two counts, deliberately. A fast approximate count shown publicly within seconds, and a slower, audited count computed from the event log in batch, used for monetisation and trending. They may disagree briefly; the batch one wins. Exactly-once processing (Kafka transactions or idempotent writes keyed by window) keeps the fast one from double-counting on consumer restarts.
  • Likes use the same pattern, with one difference: the per-user record (user_id#video_id → like) is the source of truth, so toggling like, dislike, none is idempotent and the aggregate can always be rebuilt from it.

Step 13 — Search and recommendations (sketch)

Search

An inverted index (Elasticsearch-style) over title, description, tags, channel name and auto-caption text, fed by change-data-capture from the metadata database and by video.ready events. Rank by text relevance blended with engagement signals — views, watch time, freshness, channel quality — and apply visibility and region filters in the query. Shard the index by video id with replicas for read throughput; cache the results of the few thousand most common queries for a minute. The index is allowed to be seconds to minutes behind the database.

Recommendations

The home feed and "up next" drive most watch time on large platforms, so name the architecture even if you do not design the models. It is a funnel:

  1. Candidate generation (offline and nearline) — narrow hundreds of millions of videos to a few hundred per user from several sources: embeddings learnt from co-watch patterns ("people who finished this also finished…"), subscriptions, trending in the user's region, and recent searches. Nearest-neighbour search over video embeddings does the heavy lifting.
  2. Ranking (online, per request) — a model scores each candidate using user features, video features and context (device, time of day), optimising for expected watch time or satisfaction rather than clicks, which would reward clickbait.
  3. Re-ranking and policy — diversity (not ten videos from one channel), freshness, removing already-watched items, and safety filters.

Precompute each active user's candidates in batch and store them keyed by user; run the ranker online within a ~100 ms budget; and if the recommender is down, fall back to a cached trending list for the region. Recommendations are always a degradable feature.

Step 14 — Access control and DRM

  • Signed URLs or cookies for every video. The playback service issues a token containing the video id, an expiry of a few hours, optionally the viewer's IP range or session, and an HMAC signature. The edge checks the signature with a shared key, locally. Without it, a segment URL copied into a forum is a free, permanent download link.
  • Private and unlisted videos are enforced at /play. Making a video private bumps its manifest_version, so outstanding tokens point at a path that no longer resolves, and cached copies expire. This is the one place where eventual consistency must be short and bounded.
  • DRM for premium content. Segments are encrypted once with AES under Common Encryption (CENC, with the cbcs scheme now supported across the major systems), so a single set of encrypted CMAF files serves Widevine (Chrome, Android), FairPlay (Apple) and PlayReady (Windows, many TVs). The player asks the license server for the content key; the license server checks entitlement, issues a key bound to the device's secure hardware, with rules such as expiry, maximum resolution and offline allowance.
  • Key design: separate keys per video and often per resolution tier, so a leaked key for a weakly protected 480p device does not unlock 4K, which is only licensed to devices with hardware-backed security. Rotate keys for long content, and keep the key store behind the license server only.
  • Honest limits: DRM raises the cost of copying; it does not prevent screen recording. Forensic watermarking (per-session invisible marks) is how premium platforms trace leaks.

Step 18 — Observability

  • Quality-of-experience metrics, from the player: video start time, rebuffering ratio (stalled time over watch time), video start failures, average delivered bitrate, and switches per minute. Slice them by ISP, region, device, CDN PoP and app version — most real incidents appear as "rebuffering up 3x on one ISP in one city".
  • Delivery metrics: cache hit ratio per tier, origin egress, shield request collapse ratio, edge error rates and time to first byte.
  • Pipeline metrics: upload success rate and resume rate, time from upload complete to first playable and to full ladder (p50 and p99, by duration bucket), queue depth per priority lane, task retry and dead-letter rates.
  • Business metrics: watch time per session, abandonment during startup. A regression that adds 500 ms to start time shows up here before anywhere else.
  • Alert on symptoms: page on "video start failures above 1% in a region" or "time to first playable p99 above 10 minutes", not on individual server CPU.

The trade-off summary — how to close

  • Bytes never go through the application tier. Pre-signed URLs for upload, CDN for playback. We pay with a slightly more complex client (multipart, manifests) and gain a design where the application only handles JSON.
  • Segmented HTTP streaming, not a streaming API. Static, immutable, cacheable segments let any cache serve them. We pay with a small startup overhead (manifest fetches) and gain every CDN on earth.
  • Chunked, parallel transcoding with priority. Watchable in about a minute, 4K in minutes. We pay with a DAG orchestrator and a tiny compression loss at chunk boundaries.
  • H.264 for all, expensive codecs for the popular few. Compute is spent where views make it pay back.
  • Metadata sharded by video id, hot rows cached. Sharding balances storage; caching handles virality. The per-channel listing becomes a secondary index.
  • A multi-tier CDN with ISP-embedded edges and push placement. The single largest cost lever in the system.
  • Counts via stream aggregation, not row updates. Fast approximate numbers for display, exact numbers in batch.
  • What I would build first: a single-region pipeline with managed transcoding and a commercial CDN, H.264 only, one metadata database. Build your own edge and per-title AV1 only when the egress bill justifies it — which, at this scale, it quickly does.
