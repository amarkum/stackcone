Unique ID Generator

Almost every distributed system needs unique IDs: tweets, orders, short-URL codes, chat messages. The interview question is: generate billions of unique IDs per day, roughly time-ordered, from many servers, with low latency.

1. Requirements

  • Functional: IDs unique, 64-bit (fit in a bigint), roughly sortable by time so new records appear after old ones without a separate timestamp index.
  • Non-functional: tens of thousands of IDs per second, no single coordinator on the hot path, IDs not easily guessable if they are public (or hide them behind a separate public token).

2. Options that fail at scale

  • Auto-increment in one database: unique and ordered, but one primary is a bottleneck and a single point of failure. Multi-primary auto-increment collides unless you use step/offset hacks.
  • UUID v4: unique, no coordinator, 128 bits, not time-ordered, random inserts blow up B-trees. Fine for internal keys; poor as a clustered primary in MySQL.
  • Ticket server (Flickr): a DB table that hands out ranges. Simple; still a bottleneck unless you cache ranges on each app box.

3. Snowflake

Twitter's Snowflake (and clones: Sonyflake, Instagram's ID, Discord) packs a 64-bit integer:

  • 1 unused sign bit
  • 41 bits of milliseconds since a custom epoch (~69 years)
  • 10 bits of worker id (datacenter + machine, 1024 workers)
  • 12 bits of sequence per millisecond per worker (4096 IDs/ms/worker)
EPOCH = 1704067200000  # 2024-01-01 UTC in ms
WORKER_ID = 17

_last_ms = 0
_seq = 0

def next_id(now_ms: int) -> int:
    global _last_ms, _seq
    if now_ms == _last_ms:
        _seq = (_seq + 1) & 0xFFF
        if _seq == 0:
            now_ms += 1          # sequence overflow: wait next ms
    else:
        _seq = 0
    _last_ms = now_ms
    ts = now_ms - EPOCH
    return (ts << 22) | (WORKER_ID << 12) | _seq

sid = next_id(1_735_000_000_000)
print(sid, sid.bit_length())
print("time ms", (sid >> 22), "worker", (sid >> 12) & 0x3FF, "seq", sid & 0xFFF)
Output

Each process has a unique worker id. IDs are generated in memory with no network hop on the hot path.

4. Deep dives interviewers expect

  • Clock skew: NTP can jump backwards. If now < last_ms, refuse to mint IDs or wait. Some systems store last timestamp on disk.
  • Worker id assignment: ZooKeeper, etcd, or a small SQL table. Restarting a box must not reuse an id still in the clock-skew window.
  • Capacity: 1024 workers × 4096 seq × 1000 ms = ~4 million IDs/sec. State this number.
  • Public exposure: Snowflake leaks create time and datacenter. If that is a problem, encrypt the id or use an opaque mapping.

5. Ticket ranges (good backup answer)

Each app server asks a ticket service for a block (for example 1,000 ids), then hands them out locally. One extra network call per thousand IDs. Collisions cannot happen if ranges do not overlap. You lose strict time order across servers, which is often fine for URL codes.

How to present it

List UUID vs ticket vs Snowflake, pick Snowflake for time-ordered 64-bit ids, draw the bit layout, then mention clock skew. That is a complete answer.

Try it yourself

You need unique IDs for 10,000 URL-shortener writes per second, 7-character public codes, not time-ordered. Is Snowflake the best choice? What would you use instead?
