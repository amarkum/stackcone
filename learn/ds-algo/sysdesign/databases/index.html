The database is usually the hardest part of a system to scale, because it holds state that must stay correct. Choosing the right kind — and knowing how to copy and split it — is core to every case study that follows.

SQL versus NoSQL

  • Relational (SQL): PostgreSQL, MySQL. Tables, joins, ACID. Default for most products.
  • Document (MongoDB): flexible JSON, read as a whole document.
  • Key-value (Redis, DynamoDB): lookup by key, huge QPS.
  • Wide-column (Cassandra): write-heavy, partitioned by key, time-series and chat.
  • Graph (Neo4j): social graphs and recommendations.
  • Search (Elasticsearch): full-text and analytics, not a source of truth.
  • Object storage (S3): blobs — images, video, backups.

Start with PostgreSQL. Add a specialized store only when a number or access pattern demands it.

flowchart TB W[Writes] --> P[(Primary)] P --> R1[(Replica 1)] P --> R2[(Replica 2)] R1 --> Reads R2 --> Reads P -.->|when primary is full| S1[(Shard A)] P -.-> S2[(Shard B)]

Copy first for reads and failover. Split (shard) only when one primary cannot hold the data or the write rate.

Replication

One primary takes writes and streams to replicas that serve reads. Replicas can lag, so read-your-writes traffic (the profile you just saved) should hit the primary. Synchronous replication is safer and slower; async can lose the last few writes on crash.

Sharding

Each shard holds a subset of rows. The shard key decides where a row lives. A bad key (country=US) creates a hot shard. Cross-shard joins and transactions become painful, so delay sharding.

def shard_for(user_id: int, shards: int = 8) -> int:
    return user_id % shards          # simple hash sharding

print(shard_for(1234))            # user 1234 lives on shard 2
Output
2

Adding shards with modulo remaps most keys. Consistent hashing (lesson 2) or a lookup table of key ranges moves less data. Directory-based sharding stores user_id → shard so you can rebalance without a formula.

CAP and isolation

During a partition you pick consistency or availability. Isolation levels (read committed, repeatable read, serializable) are the SQL version of the same trade-off. Feeds can be eventually consistent; payments should not.

Indexing and denormalization

Indexes speed lookups and slow writes. At feed scale you denormalize: store a precomputed timeline or a counter so reads do not join five tables. You then pay to keep copies in sync with workers or change-data-capture.

Rule of thumb

Vertical scale first, then replicas and cache, then split by service, and shard last.
