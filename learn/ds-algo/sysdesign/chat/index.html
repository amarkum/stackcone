Design WhatsApp or Facebook Messenger: 1:1 chat, group chat, online presence, delivery receipts, and message history that never drops a send.

1. Requirements

  • Functional: send/receive text (and later media), 1:1 and groups (up to hundreds, WhatsApp-style; thousands is a broadcast channel), last-seen / typing, delivered and read receipts, unread counts, message sync on a new phone.
  • Non-functional: low one-way latency (100–200 ms regional), messages must not be lost (at-least-once to the device, exactly-once in the UI via client ids), order per conversation, multi-device optional (WhatsApp originally one device; Messenger multi-device).

2. Connection model

Each mobile client keeps a WebSocket (or MQTT, which WhatsApp used) to a connection server. HTTP polling is too slow and wasteful. Connection servers are stateful: they hold sockets. A user-to-server map in Redis (user_id → conn_server) lets any API box find the socket. If the user is offline, the message sits in a inbox / queue until the next connect.

flowchart LR M[Mobile] -->|WebSocket| CS[Connection servers] CS --> CH[Chat service] CH --> MQ[(Kafka / queues)] CH --> Store[(Message store)] MQ --> CS2[Recipient connection server] CS2 --> M2[Recipient] CS --> Pres[(Presence Redis)]

Sends go through a chat service that persists first, then fans out to online sockets. Offline users get the inbox on reconnect.

3. Storage

conversations(conv_id, type, created_at)
members(conv_id, user_id, last_read_id, role)
messages(conv_id, message_id, sender_id, body, created_at, media_key)
-- PK / partition key: conv_id
-- clustering: message_id (Snowflake, time ordered)

inbox(user_id, conv_id, message_id)   -- for offline fan-out

Partition messages by conversation_id so a thread is one Cassandra/Dynamo partition (or one Postgres shard). Time-bucket huge groups (conv_id + yyyymm) to avoid hot partitions. Media: client uploads to S3 via pre-signed URL; the message body stores the key. End-to-end encryption (WhatsApp) means the server stores ciphertext and cannot search bodies — mention it if asked, do not build a search index on plaintext.

4. 1:1 send path

  1. Client sends {client_msg_id, conv_id, body} on the socket (idempotency key).
  2. Chat service persists the message (dedupe on client_msg_id), assigns Snowflake message_id.
  3. Ack the sender (sent). Look up recipient connection. If online, push; wait for delivered ack; else write inbox.
  4. Read receipt is a small event when the UI actually shows the message; it fans out the same way.

5. Groups

For a group of size G, a naive design writes G copies. Better: store one message in the group partition; fan-out notifications to members' connection servers (or inboxes). Very large 'groups' become channels: subscribers pull, you do not maintain 2 million inboxes per post.

6. Presence and typing

Heartbeat every 15–30 s into Redis with a short TTL. Typing is an ephemeral event — pub/sub, not durable. Do not hit the message store for either.

Never lose a send

Persist then fan-out. If you push first and crash, the message vanishes. Client retries with the same client_msg_id so a double persist is a no-op.

Try it yourself

A group has 50,000 members. A user sends one text. How do you store it and how do you notify members without writing 50,000 message rows?
